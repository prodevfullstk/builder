## 1. Executive Mandate & Authoritative Mutation Chain

This document defines the strict, non-negotiable requirements for closing all remaining production gates in the AI generation, verification, and mutation pipeline.

### 1.1 The Authoritative Mutation Invariant
An authoritative project mutation may occur **only and exclusively** when the complete verification chain:

$$\text{Prompt} \longrightarrow \text{Intent} \longrightarrow \text{Candidate} \longrightarrow \text{Static Validation} \longrightarrow \text{Native Build} \longrightarrow \text{Runtime Verification} \longrightarrow \text{Required Acceptance Verification} \longrightarrow \text{Evidence} \longrightarrow \text{CAS Commit}$$

has completed successfully.

If any mandatory stage is **unavailable, missing, forged, stale, simulated, or failed**:
**AUTHORITATIVE COMMIT MUST NOT OCCUR.**

Under no circumstances may an AI response stating "done", a simulated test score, a client-provided success claim, or a default-success fallback (`nativeBuildStatus || "passed"`) be accepted as proof of correctness or permitted to trigger project mutation.

## 2. Gate 1 — Native Build Must Be Authoritative

### 2.1 Explicit Non-Default States
The build verification pipeline and commit service must strictly require:
```ts
nativeBuildStatus === "passed"
```
explicitly present and cryptographically evidence-bound.

The build state model must distinguish:
```ts
export type NativeBuildStatus = 
  | "passed"
  | "failed"
  | "unavailable"
  | "not_run"
  | "stale"
  | "invalid";
```

### 2.2 Rules & Invariants
1. **Zero Default-Success**: Never perform `runtimeContext.nativeBuildStatus || "passed"` or any equivalent defaulting.
2. **Fail-Closed Commit Gate**: Only `"passed"` satisfies the authoritative build gate. All other states (`"failed"`, `"unavailable"`, `"not_run"`, `"stale"`, `"invalid"`, `undefined`) strictly reject commit.
3. **Evidence Binding**: Build evidence must be bound to `candidateHash`, `projectId`, and `projectRevision`. Evidence with mismatched hash, stale revision, mismatched project, or timestamp predating candidate creation must be rejected.

## 3. Gate 2 — Real Runtime Verification

### 3.1 Lifecycle Requirements for Supported Frameworks
For supported frameworks (Next.js, Vite React, Astro SSG), where runtime execution is applicable, verification must execute the complete runtime lifecycle:
1. Prepare project workspace in isolated microVM sandbox.
2. Install dependencies (`npm install` / `pnpm install`).
3. Execute native build (`npm run build`).
4. Start the generated application using the framework's real runtime/start command (`npm run start` or `npm run preview` or framework dev/prod server).
5. Wait for server readiness (polling port / healthcheck endpoint).
6. Perform real HTTP smoke verification (HTTP GET against the running local server, asserting HTTP 200 and expected HTML payload).
7. Capture execution metadata: command, exit status, stdout/stderr summary, startup status, URL/port, HTTP status code, timestamp, candidate hash, project ID, project revision.
8. Terminate the child process.
9. Clean up the sandbox container.

### 3.2 Invariants
- Do not claim runtime verification if only `build` was executed.
- Runtime evidence must be generated by the actual execution service—never caller-supplied.
- Evidence must be bound to: `projectId`, `revision`, `candidateHash`, `evidenceId`, `framework`.

## 4. Gate 3 — Visual Verification Must Be Real

### 4.1 Elimination of Simulated Visual Scores
- Remove caller-provided values (`hasScreenshotService`, `screenshotCaptured`, `simulatedScore`) from the authoritative path.
- Simulated scores or mocked screenshot booleans must never satisfy visual verification.

### 4.2 Real Visual Verification Protocol
For any visual-edit or screenshot recreation task:
1. Generate candidate files.
2. Validate and build candidate in microVM.
3. Start candidate application.
4. Capture an actual screenshot using a real headless browser or screenshot mechanism.
5. Derive `renderedImageHash` from the actual captured image bytes.
6. Compare with `referenceImageHash` where a reference exists using an image perceptual/pixel diff.
7. Produce structured visual evidence:
```ts
export interface RealVisualEvidence {
  referenceImageHash?: string;
  renderedImageHash: string;
  screenshotEvidenceId: string;
  comparisonMethod: string;
  comparisonScore?: number;
  viewport: { width: number; height: number };
  candidateHash: string;
  projectId: string;
  revision: number;
  timestamp: string;
}
```

### 4.3 Fail-Closed on Unavailable
If no real screenshot service is available, visual verification status must be `VISUAL_VERIFICATION_UNAVAILABLE` and an authoritative visual mutation must fail closed.

## 6. Gate 5 — Remove Human-Language Keyword Gating

### 6.1 Semantic Intent Classification
- Eliminate English and Bengali hardcoded regex routing dictionaries (`বানাও`, `তৈরি`, `কোড`, etc.).
- Natural language intent must be classified semantically by model / structured LLM classifier into canonical `AgentIntent`:
  `CREATE_PROJECT | ADD_FEATURE | MODIFY_FEATURE | FIX_BUG | REFACTOR | EXPLAIN | QUESTION | CONTINUE_BUILD | VISUAL_RECREATE | INSPECT`.
- Server validates structured intent against strict schema.

### 6.2 Truthful Classification Provenance
- Field `source`: `"model" | "heuristic" | "user"`.
- Never manufacture fake confidence (e.g. hardcoded `0.95`). Expose confidence only when emitted by the classifier.
- If semantic classification cannot be performed, enter an explicit degraded/unverified path. Heuristic fallback must never authorize mutation without user confirmation.

### 6.3 Multilingual Invariant
The semantic classifier must correctly interpret user requests across diverse languages (English, Bengali, Hindi, Spanish, French, Arabic, Japanese, etc.) without per-language regex dictionaries.

## 7. Gate 6 — Monaco Authoritative Mutation Path

### 7.1 Centralized Pipeline Routing
Monaco "Ask AI" (`components/builder/code-editor.tsx`) must not bypass the centralized candidate commit/CAS boundary:
- Eliminate direct client mutation `updateFile(activeFile, proposedContent)`.
- Route Monaco edits through the authoritative pipeline:
  `Monaco Request → Semantic Intent → Workspace Context → Candidate Patch → Scope Validation → Static Validation → Native Build → Runtime/Acceptance Verification → Evidence → Server-Authoritative CAS Commit → Client State Refresh`.

### 7.2 Multi-File Candidate Capability
- Monaco Ask AI must not be restricted to single-file output (`files.find(f => f.path === activeFile)`).
- Model may propose multi-file candidate patches where necessary, validated through `ScopeEnforcer` and committed atomically.

## 8. Gate 7 — Acceptance Verification Matched to Criterion Type

### 8.1 Explicit Criteria Classification
Acceptance criteria must be classified into:
```ts
export type CriterionClass = "static" | "build" | "runtime" | "behavioral" | "visual";
```
- Source token inspections (`isOpen`, `onClick`, `md:hidden`) are valid **only** for `static` criteria.
- `behavioral` criteria require running application interaction (e.g. headless browser or runtime harness setting viewport, clicking hamburger button, verifying navigation visibility and DOM state).

## 9. Gate 8 — Real End-to-End Scenarios

The system must prove 4 primary real scenarios through the actual production code paths:
- **Scenario A (Create)**: SaaS landing page with responsive navigation, hero, pricing, testimonials, footer. Verified through intent, candidate, build, runtime HTTP smoke, evidence, and CAS commit.
- **Scenario B (Specific Edit)**: "Make navbar logo 20% smaller". Surgical retrieval, minimal scope (1 file touched), delta verified, build/runtime verified, CAS commit.
- **Scenario C (Behavioral Feature)**: "Add mobile hamburger menu". Interactive behavioral verification of click toggle, nav visibility, and desktop preservation.
- **Scenario D (Visual Recreation)**: Screenshot input with reference image, VisualSpec generated, runtime started, real screenshot comparison, evidence bound, CAS commit.

## 10. Gate 9 — Native Build Failure Blocks Commit

Deliberately broken candidate (TypeScript error, syntax error, missing import) traversing the actual pipeline:
- Native build fails with non-zero exit code.
- Commit service strictly rejects mutation.
- Workspace files and project revision remain completely unchanged (zero partial mutation).

---

## 11. Gate 10 — Native Unavailable Blocks Authoritative Commit

When microVM sandbox is unconfigured or unreachable:
- Authoritative commit is strictly rejected.
- No silent fallback (`nativeBuildStatus || "passed"`).
- Candidate may be stored as an uncommitted `DRAFT / UNVERIFIED` only, without mutating project state.

## 12. Gate 11 — Evidence Integrity & Cryptographic Binding

Every validation evidence record must be server-generated and immutably bound to:
1. `projectId`
2. `projectRevision`
3. `candidateHash` (SHA-256 of candidate files)
4. `intentId`
5. `criterionId` (where applicable)
6. `verificationType` (`"static" | "build" | "runtime" | "behavioral" | "visual"`)
7. `createdAt` (ISO timestamp)
8. `expiresAt` (15-minute TTL)

Commit service must strictly reject:
- Mismatched candidate hash.
- Mismatched project ID.
- Stale or mismatched revision.
- Expired evidence token.
- Evidence generated prior to candidate timestamp.
- Client-forged success fields.

## 13. Gate 12 — Provider & Vision Fallback

If a request requires vision capabilities and no vision-capable provider/model is available:
- Reject the authoritative visual operation, OR
- Return an explicit `UNVERIFIED_VISION` state that cannot commit.
- Silent downgrade to text-only model claiming visual success is prohibited.
